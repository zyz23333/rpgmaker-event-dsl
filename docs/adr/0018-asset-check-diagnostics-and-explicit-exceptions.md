# Keep asset-check findings explicit while allowing narrow authoring exceptions

The event-use coverage in [ADR 0016](0016-event-rooted-asset-use-coverage.md) and exact file contract in [ADR 0017](0017-exact-asset-file-existence-in-editing-projects.md) do not establish diagnostic severity. We choose checking by default in both Compile and Compile Check, with confirmed missing paths, case mismatches, and wrong file types blocking ordinary explicit asset uses, while the same findings in Conditional Asset Candidates and explicitly inactive saved configuration warn. This preserves a useful strict default without treating every saved initial name or disabled setting as a current runtime requirement. Unsupported names, asset-path links, encrypted modes, necessary input failures, inaccessible metadata, and observed inconsistencies remain errors even for candidates or inactive settings. Supported dynamic and cycle stopping points remain informational rather than being presented as successful checks.

An Asset Check Exception may downgrade only the confirmed missing-path, case-mismatch, or wrong-type findings for one exact namespace and original name, with a required reason. It affects all uses of that target, leaves each finding and reason visible, and does not modify saved state. We choose these explicit exceptions over a global off switch, global warning mode, wildcard exceptions, or exceptions scoped to one event location. Malformed or duplicate exception entries fail configuration validation; after complete relevant checking, an entry that downgraded no error warns that it currently has no effect. Unsupported forms, incomplete checks, and existing reference or Script Command Gate failures cannot be waived. This deliberately permits a valid saved name or inactive setting to block compilation when its asset form is outside the selected checking support, without repairing that saved state or claiming the form is invalid native data.

File-query reuse and grouped presentation retain each use, dependency chain, condition, and individual diagnostic result. A group takes the highest effective severity of its members without losing their separate levels. Independent safe checks continue after an asset error, while affected paths stop explicitly and the report distinguishes incomplete checking from success. Exceptions do not establish file existence or runtime loading, and do not authorize rewriting external project data. Formal and recognized raw inputs share the same policy. Compile errors prevent new output publication, and Compile Check remains read-only.

The user confirmed Q1–Q11 and then the consolidated contract, shared understanding, and completion boundary on 2026-10-24 in [the diagnostic policy ticket](../../.scratch/asset-validation/issues/04-asset-diagnostics-and-policy.md#answer). The ticket is resolved and this ADR is accepted. It refines ADR 0011/0012's selected file-check policy while preserving saved values and ownership. The subsequently accepted [workflow ticket](../../.scratch/asset-validation/issues/05-workspace-asset-check-lifecycle.md#answer) and [ADR 0019](0019-asset-checks-at-workflow-boundaries.md) establish coherent inputs, repeated check points, and live asset conditions separate from Generated Freshness. Push applies this same policy to uses reconstructed from verified generated events and the corresponding snapshot. An observed relevant change is an unwaivable consistency failure even if the later file condition improves or both individual findings would otherwise warn. Recovery bookkeeping does not certify assets; a current asset check may still fail after completed data writes have been recorded. No product implementation, executed product tests, or native acceptance is claimed.
