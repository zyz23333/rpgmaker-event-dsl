# Check live asset conditions at compilation and push boundaries

Event asset names depend on event state and selected standard-data relationships, while their files exist outside the Standard Project Data Snapshot. We choose a coherent compilation view: current DSL-owned event relationships come from the Staged Data Graph, external relationships and necessary System settings come from the same captured Project Data Snapshot, and file queries inspect the bound live Project Root. Reading newer live database fields alongside older compiled inputs would validate a different event state. An unpulled standard-data change remains Project Drift for Push to reject; it is not silently merged into asset checking. Necessary external field reads neither expand ownership nor validate unrelated fields.

Compile and Compile Check apply the accepted asset policy, and Push must check live asset conditions again before authorizing new writes, including when there are no affected files. Diff retains its data comparison and existing integrity/freshness checks without querying live asset files. Clone, Pull, and DSL Decompilation retain their existing capture and expressibility/reference checks without adding an asset-file gate, so missing files do not prevent obtaining source for repair. Asset files remain outside snapshots, copying, and Push writes. This preserves review and takeover while requiring a fresh asset judgment at operations that validate or apply event output.

Live asset-file observations do not enter the persistent Compile Baseline. Generated Freshness establishes the origin of generated data, not current asset availability; asset-check configuration and the Compile Contract Version remain compilation inputs. A file restored after a failed Push may pass the next Push without recompilation if other inputs remain current. Push reconstructs uses from the verified Generated Project Data and its corresponding captured snapshot, preserving native origins and dependency chains, rather than recompiling DSL or trusting a historical asset report. This separates a repeatable event output from a fresh judgment about external file conditions.

Compile Check rechecks asset observations before successful return. Compile rechecks before publishing generated data and before committing its Sync Manifest; an observed relevant change fails the operation and requires a rerun, even when the later condition has improved. Existing publication-failure boundaries apply. Push checks before its first Project Root replacement and again after all replacements, before synchronization metadata is refreshed. A post-write asset error or observed inconsistency leaves an Interrupted Push without automatic rollback. A no-write Push checks before returning and does not create pending state merely because an asset check fails. These are observable check points, not isolation from external writers.

Relevant observations are exact path and name matches, required path-component types and links, observable metadata, and the location and nature of any failure. Content, size, modification time, or file identity changes do not invalidate an unchanged existence judgment, and unrelated directory entries do not matter. Queries may be shared within one check point while retaining every use and origin; each later check point and command obtains new filesystem observations. Fixed-data dependency expansion may be reused. We accept that a change and restoration between observations can escape detection, rather than introducing media hashing, directory-wide invalidation, or continuous monitoring.

Push also rechecks its captured source and validation dependencies, relevant configuration, snapshot, generated data, and Project Root Binding at write/completion boundaries, alongside existing standard-data checks. It does not adopt new exceptions or switch targets mid-operation. Same-Workspace exclusion and explicit Pull rebinding remain in force without cross-Workspace coordination. An observed change prevents new replacements or leaves pending state if replacements have begun.

Recovery records what happened to project data before judging whether another Push can succeed. With understood, consistent evidence and the original binding, all affected files matching generated data allow synchronization bookkeeping to finish even if assets are still missing; all matching snapshot data allow abandonment, while mixed, missing, or unknown states retain the existing refusal. Recovery preserves the original compilation basis and does not certify assets or authorize new writes. Normal current freshness, drift, and asset checks follow; they may fail after pending state has been cleared. This avoids making a lost asset permanently trap already completed data writes in recovery.
