# Check current asset files before validation or application completes

Event asset names come from coherent standard-data inputs: Compile/Check use current staged events and the captured Project Data Snapshot for external relationships and necessary System settings; Push uses verified Generated Project Data and its corresponding captured snapshot. File queries inspect the bound live Project Root. Unpulled standard-data edits remain Project Drift; newer live fields are never mixed into the captured dependency view. Asset files remain outside snapshots, copying, backups and Push writes.

Each operation performs one complete asset-check pass at its gate. Compile checks after complete candidate validation and before local output publication; Check checks before returning. A writing Push checks after staging and before creating pending state or replacing the first project file, once the existing integrity, freshness and drift prerequisites pass. A no-write Push checks before returning. Each new command queries current files; shared target/directory queries may be reused within its pass. Early input failures can prevent the pass and must report that it did not run. Diff, Clone, Pull and DSL Decompilation add no asset-file gate.

The result describes that pass's observations, not an atomic media-tree snapshot or a promise that files remain unchanged until command completion. We do not compare earlier and later asset observations, recheck before Compile's Manifest commit, or recheck after Push writes. A repaired file is judged by its current facts, not rejected because it changed. A contradictory individual query remains a query failure; media contents, timestamps, identities and unrelated directory entries are not tracked. There is no media hashing, continuous monitoring or cross-process isolation.

Live asset conditions do not enter Compile Baseline or Generated Freshness. Asset policy and Compile Contract Version remain compilation inputs. A restored file can allow a later Push without recompilation when those inputs remain current. Push reconstructs event-local uses under ADR 0016 without reevaluating DSL or trusting an old asset report.

All existing source, validation-dependency, configuration, snapshot, generated-data and Project Root Binding protections remain, including the full standard-data drift checks and affected-file old-content checks at write/completion boundaries. Those inputs determine generated bytes or write authority; their changes still prevent publication/writes or leave Interrupted Push after writing begins. Asset availability alone neither creates nor retains pending state. Once data writes and their evidence are consistent, normal synchronization bookkeeping completes without a post-write asset condition.

Recovery remains content-based under ADR 0006/0013: understood evidence and the original binding allow all-generated completion or all-snapshot abandonment; mixed, missing, unknown or inconsistent states refuse automatic recovery. Missing assets do not prevent recording completed data writes. Recovery preserves the original compilation basis; the new Push then runs its ordinary current freshness, drift and asset gate, even with no changes. Recovery success does not certify assets.

The user requested this revision on 2026-10-25 after reviewing overdesign. It replaces the 2026-10-24 decisions to compare observations at multiple checkpoints, fail even on improvement, and retain pending after post-write asset failure. Assets are read-only validation conditions, not generated-content inputs or Push write targets; repeated equality checks added recovery states without providing isolation. [Ticket 05](../../.scratch/asset-validation/issues/05-workspace-asset-check-lifecycle.md#answer), the specification and acceptance matrices carry the revised contract. No product implementation or acceptance execution is claimed.

The 2026-11-02 revision of ADR 0016/0018 reduces the first-release coverage and report requirements. It does not change these workflow gates, compilation-policy baselines or recovery protections. Deferred capabilities do not block delivery of the retained scope.
