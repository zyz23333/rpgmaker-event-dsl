# Windows / Node 22 automation baseline

Ticket 02 uses the same independent Common Event project fixture as ticket 01. It runs the actual CLI in separate Node processes from a unique Workspace directory containing Chinese characters and spaces. Normal `pnpm check` exercises the TypeScript CLI. After `pnpm build`, `pnpm --filter rpgmaker-event-dsl test:windows-baseline` repeats the same four CLI tests against `dist/cli.mjs` and resolves real emitted package declarations. No installed editor, runtime, assets or local `references/` directory is required for these data-only operations.

The full sequence is init → Clone → Decompile → Check → Compile → Diff → no-op Push → edit actual Decompiled Source → Compile → Push. It compares complete parsed data to the independent fixture, checks actual Discovery through the compile manifest, verifies Check publishes nothing, observes a real CommonEvents file replacement, and checks invalid-option stderr/exit status and final user source, Project Root, Generated Project Data, Snapshot and manifest. The separate junction case requires a real Windows directory junction and invokes the aliased CLI entry for both source and built artifacts. EPERM, EACCES, missing binaries, wrong platform/runtime and process timeouts fail visibly.

## Reusable temporary filesystem and process convention

`packages/rpgmaker-event-dsl/test/support/windows-sandbox.ts` is test-only support. `withWindowsSandbox` owns one random directory beneath `os.tmpdir()/rpgmaker-event-dsl-windows/` (override with absolute `MV_WINDOWS_TEST_OUTPUT`), and creates all game/workspace paths beneath it. CI uses `runner.temp`. Do not create shared siblings outside the owned random directory. `createMinimalProject` reconstructs the independent project files and links actual package declarations through a directory junction. `runCli` starts `process.execPath` without a shell, uses an absolute source/built entry and loader, hides helper windows, enforces a 15-second child deadline, and records command, arguments, cwd, timestamps, stdout, stderr, exit code and signal. A timeout has a non-success result even when no numeric exit code is available.

On success the owned sandbox is removed after checking that its resolved root still matches the original root and remains under the selected parent. On any failed assertion or subprocess, the complete sandbox and `process-results.json` remain, and the runner prints its absolute path. `MV_KEEP_WINDOWS_SANDBOXES=1` also retains successful sandboxes for investigation. Retained evidence is not cleaned by another test or automatically promoted to a pass; remove it only after reviewing/copying the needed failure evidence. Node's recursive removal unlinks directory junctions rather than traversing the package target.

Each indexed case also calls the shared `recordEvidence` support, which writes immutable result JSON under `test-results/mv-evidence/` (`MV_EVIDENCE_OUTPUT` override). Passing records include raw subprocess transcripts before successful sandbox cleanup. Their source fingerprint now captures all source and test inputs, relevant configuration and CI files; built runs additionally hash all emitted distribution files. Source and built executions remain separate records. CI runs only `windows-latest` / Node 22, checks the full suite, builds, runs the built CLI cases, then uploads both `test-results/` and the explicit temporary sandbox parent even on failure.

## Execution scope

Ticket closure records the actual locally observed Windows / Node 22 checks and reviewed result filenames in ticket 02. The configured GitHub-hosted workflow is not claimed to have run until its hosted run exists. These synthetic Workspace cases establish no REA editor finding and no actual game behavior; those remain separately identified obligations.

An earlier probe placed the sandboxes beneath the repository's `test-results/` directory and observed intermittent Windows EPERM during Compile generated-directory and Push pending-directory renames. Both failed run records are preserved as failures. A six-run standalone probe at that location failed once; switching only the sandbox parent to OS temp passed six consecutive runs. The underlying contention source was not identified, so these observations do not establish that repository-local directory replacement is repaired. The baseline now uses the intended isolated OS temporary filesystem; no product retry, exception swallowing or weakened assertion was added. Directory publication and replacement failure behavior remains mandatory in tickets 19–22.
