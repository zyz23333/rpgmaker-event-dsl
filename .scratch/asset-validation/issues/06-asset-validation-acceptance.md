## Question

前置输入：[事件直接与间接素材依赖的检查边界如何统一](02-direct-asset-reference-coverage.md)、[素材文件存在性应如何判定](03-asset-file-existence-contract.md)、[素材检查结果如何诊断并影响编译](04-asset-diagnostics-and-policy.md)与[素材检查如何接入 Compile 与 Push 并保持结果有效](05-workspace-asset-check-lifecycle.md)。

基于已决的覆盖、文件判定、诊断和工作流契约，怎样证明首版事件直接及可静态追踪的间接素材文件存在性检查符合承诺，并达到可编写实施规格的完成门槛？

确定独立预期的最小素材/事件 fixture、类别与保存位置覆盖、正式/已识别 raw 一致性、None 与未启用配置、Windows 文件名/路径边界、缺失与不可确认结果，以及 Compile Check 无发布、Compile 失败隔离和已选择的 Push 检查时机。只验证文件存在性，不以通过检查宣称图片布局或媒体播放有效。

增加间接依赖矩阵：采用已决关系清单中的动画图片/SE、图块组等用例，验证条目存在但文件缺失、必要字段与合法空值、完整来源链、重复关系、追踪停止条件和动态未知边界。若已决范围不包含某关系，记录原因，不能仅凭规划用例宣称已支持。

加入操作相关性的反例，证明“修改角色 HP”不会仅因引用 Actor 就无条件把其全部图像缺失当作该操作错误；未被事件引用的无关数据库条目不应触发全库检查。分别验证标准数据中的素材名称变化、文件增删、Pull 与 Push 对间接检查结果有效性的影响，且检查不改写外部项目数据。

区分自动化、必要的首方行为核对和实际产品验收责任；确定哪些原生加载事实需要实际运行验证，以及后续发现反例如何重开决定。形成精确的规格交接门槛和实施顺序约束，不在此票实现功能或把计划中的测试记为已通过。

### 1. 验收对象与独立预期

验收以前置四份已接受契约为依据：[事件直接与间接素材依赖的检查边界如何统一](02-direct-asset-reference-coverage.md#answer)、[素材文件存在性应如何判定](03-asset-file-existence-contract.md#answer)、[素材检查结果如何诊断并影响编译](04-asset-diagnostics-and-policy.md#answer)、[素材检查如何接入 Compile 与 Push 并保持结果有效](05-workspace-asset-check-lifecycle.md#answer)。首版仍限 Windows / Node.js 22 验证环境及 RPG Maker MV 1.6.1 普通编辑项目，只证明所选事件素材的文件存在性，不保证运行时加载、内容可读、图片布局、解码或播放。

每个用例的预期独立依据这些契约及首方证据编写，包含 Event Asset Uses、类别与原始名称、完整来源链、条件、问题类别、基础与有效级别，以及操作后文件和同步状态。可共用临时项目与文件构造辅助代码，不得用被测收集器、文件判定器或诊断策略生成自身预期；正式 DSL 与已识别 raw 分别对照预期，不能只比较两者相等。原版全库部署集合也不是本功能的完整预期。

### 2. 覆盖尺度与最小 fixture

每个已选直接字段、路线位置及间接关系都有正常解析和缺失素材用例，多素材字段分别证明。None、Compiler Default、必要字段损坏、候选、明确非活动配置、动态／循环停止、文件失败分类、例外和工作流检查点逐项覆盖。公共规则采用代表性组合，专门覆盖来源共享、不同级别、镜像和写后变化，不要求所有维度的完整笛卡尔积。

使用自写小型合成项目和尽量只改变一个因素的变体。配套矩阵明确直接位置、间接关系、范围反例、文件事实、诊断组合、工作流及原生运行用例。所有当前事件独立起点、未调用公共事件、当前 DSL 已移除而仅残留于快照的事件均有区别验证。修改 Actor HP、无关数据库条目、未知负载及其他已排除关系不能意外扩大扫描范围。

文件存在性用例可用空文件，并验证其允许通过；原生核对使用有效自制媒体。验证保存值和外部数据不被检查修复或改写，素材不进入 Snapshot、复制、备份或 Push 写入范围。旧成功用例需补充必要素材及标准字段，不能用批量例外或删除断言维持表面通过。

### 3. Windows 文件证据与故障验证

真实 Windows / Node.js 22 文件树负责准确目录、名称、扩展名、特殊字符、错误类型、缺目录、根别名、根以下链接及硬链接等行为；无法合法创建的 Windows 名称与 System 加密标志采用输入用例。受控错误注入负责稳定复现目录不可枚举、元数据查询失败和查询内观察矛盾，并明确不能替代真实 ACL 行为证据。

特殊文件系统能力不足时保留未执行及原因，由具备能力的环境补验；不能静默跳过后宣布全部通过。构建后 CLI 的显式用例列表必须包括素材用例。不存在把此前 Node v24 的 500 文件微测升级为本功能性能门槛或 Node.js 22 验收的依据。

### 4. 工作流与诊断验收

在确定的检查点暂停真实操作，修改素材或输入后继续执行，不靠固定延时碰阶段。联合断言诊断、退出结果、Project Root、Generated Project Data、Snapshot／Manifest 和 pending；包含真实 CLI 路径，不以内部函数模拟替代整体验证。完整场景和检查点见配套矩阵，覆盖 Compile Check 三种起始状态、Compile 发布边界、Push 写前／写后／无差异／恢复、实时素材与标准字段变化、输入及绑定改变、无关变化不失效，以及不增加素材门槛的操作。

诊断结果逐项验证稳定问题标识、阶段、类别、级别、搜索依据、完整来源与链、条件、例外原因和完整性。CLI 验证用户能够获取问题、定位、链、例外及未完成说明和正确退出结果，不锁死无意义的空格、颜色和整段排版，也不新增 JSON CLI 或通用报告接口承诺。

核对分组和使用次数、不同级别不互相覆盖、例外允许与禁止分支、无实际降级的例外、检查不完整时不作无用例外结论、失败时保留既有 warning，以及停止点不冒充成功。只有可靠的 Definition Source 位置才报告行列。更早错误使输入不可信时，不要求对残缺数据穷尽素材检查，但必须保留相应未运行／未完成说明。

### 5. 原生运行核对与责任

实施方准备并尽可能执行 Windows / RPG Maker MV 1.6.1 核对；确需人工操作的部分由项目维护者执行并留证。必验范围是代表性图片／音频／影片的目录、扩展名与实际文件定位，支持范围内中文／空格与图片／音频百分号、井号映射，以及动画双图与时序 SE、整组图块／页图块单图、敌人前视／侧视目录和一个运行时覆盖初始候选的场景。

记录 MV／宿主版本、输入、实际请求及文件定位结果。有效自制媒体用于获得可观察证据，不把播放成功当作所有素材的保证，也不把播放失败直接当作存在性规则错误。排除范围内的部署加密、子路径、影片百分号／井号和 picker 能力不要求全面实测；静态首方证据仍用于逐条关系查证，有限运行样例不替代全部自动化矩阵。

原生必验项可作为明确待执行项交接规格；产品验收时必验未执行或证据矛盾未解决，不能宣布完成。自动化由实施方执行和留证，维护者审阅整体验收报告并最终确认。

### 6. 证据状态与反例处理

每项验收记录契约出处、最小输入、操作或变化时机、预期诊断与状态、验证方式、执行责任及证据状态。已有静态源码、测试定义、受控实验分别标明能证明什么；计划、未执行和环境受限不等于通过；实际结果记录环境与证据。本轮已有依据和所有待执行项见配套清单。

实现违反契约时修实现、补独立回归预期；支持范围内新首方／运行证据推翻文件定位或消费关系依据时，保存最小复现、版本和观察结果，重开相应决策及 ADR，并核对下游诊断、工作流和验收影响；原生支持更宽或已排除关系只构成范围扩展提议，经新决定才纳入。不得通过放宽断言、改预期或增加例外把反例直接改绿。

### 7. 实施顺序与交接门槛

先建立独立预期、合成 fixture，补齐旧成功用例素材和必要字段，尽早核对可能推翻方案的原生事实；分别验证依赖收集、文件判定与诊断政策；接入 Compile／Compile Check 后完成 Push 与恢复，并验证真实变化、输入和绑定保护；更新 Compile Contract Version、使用说明及构建后 CLI 验收。内部可以分步开发，但对外宣称首版完成时整套契约必须满足。具体模块、API、配置拼写、测试文件名和实现任务拆分由后续实施规格确定，不是本票遗留的产品政策选择。

交接包由本 Answer、[逐项对照表](../acceptance-matrix.md)、证据与待执行清单、实施顺序及反例规则组成。设计完成要求材料足以编写实施规格，没有影响实现的未决政策，并由用户确认合并全文与完成边界。配套矩阵是验收设计的展开，不是实施规格或实现任务。
